## 00:00 — Opening and Objective

**Sarah Lim:**  
Thanks everyone for joining. The objective today is to align on the first version of the AML / STR case management platform. We are not trying to replace every existing AML tool in the bank. For this first release, we want a focused application that supports analysts from alert review to investigation, decisioning, reviewer approval, and STR filing readiness.

**Rajesh Menon:**  
From the compliance side, the important point is that this should look credible. AML is a regulated process. Banks are expected to have controls to detect, investigate, and report suspicious activity. We do not need a production-grade system for the first release, but the workflow should reflect how AML teams actually operate.

**Ben Chua:**  
Understood. Technically, I suggest we build a web app with seeded demo data. We can simulate alerts coming from a transaction monitoring engine, but we do not build the monitoring engine itself. The platform will start from the moment an alert becomes a case.

**Mei Ling Tan:**  
That makes sense. Analysts do not usually create every alert manually. We receive alerts generated by monitoring scenarios, rules, models, or another upstream system. The case management tool should help us make sense of the alert, review customer activity, capture investigation notes, and decide whether there is suspicion.

**Priya Nair:**  
And for STR, I want to be clear: the platform should not pretend to file directly to STRO or SONAR. It can track STR filing status and prepare the information, but direct submission would need proper production integration and approval.

**Sarah Lim:**  
Good point. So for scope: prepare and track STR filing readiness, but no real STRO / SONAR integration.

**Grace Ho:**  
From an audit perspective, the key is traceability. Who changed the case? Who added the rationale? Who approved the decision? What evidence was reviewed? If someone asks six months later why a suspicious case was or was not escalated, the platform must show the chain of reasoning.

**Daniel Wong:**  
Also workload. I need visibility across cases. I need to know what is open, what is high-risk, what is aging, what is pending reviewer approval, and which analysts are overloaded.

## 05:00 — Regulatory Context and Boundaries

**Rajesh Menon:**  
Before jumping into screens, let me ground the regulatory context. For banks in Singapore, MAS Notice 626 is the main AML/CFT notice. It sets out requirements around customer due diligence, ongoing monitoring, risk assessment, and suspicious transaction reporting.

**Rajesh Menon:**  
For the first release, we do not need to encode every regulatory requirement. But the app should clearly support AML investigation and STR decisioning.

**Sarah Lim:**  
So the product narrative is: this platform helps the bank operationalise AML case handling and STR readiness.

**Rajesh Menon:**  
Exactly. It should help us demonstrate that suspicious activity is identified, reviewed, assessed, escalated when needed, and documented.

**Priya Nair:**  
I would add one nuance. An analyst does not file an STR just because a rule fires. The alert is a starting point. The analyst investigates and determines whether suspicion is established. That decision needs rationale.

**Mei Ling Tan:**  
Yes. Sometimes an alert looks bad at first, but after checking the customer profile and business activity, it can be explained. Other times, the pattern gets more concerning as we review the details.

**Grace Ho:**  
So the system needs to distinguish between alert, case, investigation, suspicion decision, and STR filing status. Those are related but not the same thing.

**Victor Lee:**  
That distinction matters for the data model. I suggest:
- Customer
- Transaction
- AML Alert or AML Case
- Investigation Note
- STR Decision
- Audit Log

We can decide whether Alert and Case are separate entities. For a first version, we might combine them and call it AMLCase, with fields for alert type and alert reason.

**Ben Chua:**  
That will simplify the implementation. We can create an AMLCase entity that contains the alert metadata and investigation state. If we need to split later, the model can evolve.

**Rajesh Menon:**  
Good. Also include risk categories. Initially, we can include Money Laundering and Terrorism Financing. Later, the model may need to evolve if regulatory or internal policy requirements expand.

**Sarah Lim:**  
Perfect. That keeps the initial scope clean while allowing future extension.

## 15:00 — Core Workflow

**Sarah Lim:**  
Let us define the core workflow from alert to STR decision.

**Amir Khan:**  
Upstream transaction monitoring generates an alert. The alert includes the scenario name, risk score, reason codes, and linked transactions. Example scenarios:

- Unusual transaction volume
- Transactions inconsistent with customer profile
- High-risk jurisdiction exposure
- Multiple unrelated counterparties
- Dormant account suddenly active

**Mei Ling Tan:**

Then I review transaction details:
- Amounts
- Counterparties
- Countries
- Timing
- Purpose of payment

# Post-Meeting Summary

## Agreed MVP Scope

The MVP will include:

1. AML dashboard
2. AML case list
3. Case detail page
4. Customer profile panel
5. Transaction timeline
6. Risk indicators
7. Investigation notes
8. STR decision workflow
9. Reviewer approval
10. Filing status tracking
11. Audit log
12. Seed data
13. Basic role simulation
14. Tests
15. Requirements summary

## Agreed Out of Scope

The MVP will not include:

1. Real transaction monitoring engine
2. Real STRO / SONAR submission
3. Real sanctions screening integration
4. Real authentication / SSO
5. Real customer data
6. Real document upload
7. Real workflow engine
8. Full regulatory rule engine

## Key Business Rules Captured

1. An alert becomes an AML case for investigation.
2. Analyst reviews customer, transactions, risk indicators, and evidence.
3. Analyst adds investigation notes.
4. Analyst submits a recommendation.
5. Reviewer approves, rejects, or returns for more information.
6. STR decision and filing status are separate.
7. Filing reference is required when marking STR as filed.
8. All important actions must create audit log entries.
9. High-risk cases should be visible in dashboard.
10. Case list should support search, filters, and sorting.
